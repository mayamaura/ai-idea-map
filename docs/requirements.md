# アイデア拡張メモアプリ 要件定義書

**作成日**: 2026-05-27  
**バージョン**: 1.0

---

## 1. プロジェクト概要

### 1.1 アプリ名（仮）
**IdeaMap** - AIと一緒に育てるアイデアマップ

### 1.2 目的
アイデアをノード（円/カード）として配置し、線でつなぐことで思考を可視化・拡張するウェブアプリ。人間の発想とAI（Claude）の提案を組み合わせて、アイデアを深く広く展開できる。

### 1.3 対象ユーザー
- PCおよびスマートフォンで使うソロユーザー
- 自分のClaude APIキーを持つユーザー
- アイデア整理・ブレインストーミングをしたい個人

| ノード移動 | ドラッグ＆ドロップで自由移動 |

| 子ノード追加 | Tab キーで選択ノードの子ノードを作成し編集開始（Phase 22: 作成後に編集開始） |
| ノードサイズ | テキスト量に応じて自動調整 |
| ノード色 | カテゴリ選択によって自動設定（カテゴリ固有の背景色） |

#### 2.1.2 エッジ（線）操作

| 機能 | 説明 |
|------|------|
| エッジ追加 | ノードのハンドルをドラッグして別ノードに接続 |
| ドラッグ&ドロップ接続 | ノードをドラッグして未接続の別ノードに重ねる（ドラッグ中のノードの中心が相手の矩形に入る）と相手が緑色でハイライトされ、ガイド「ドロップでこのアイデアを親にして接続」が表示される。そのままドロップするとエッジが作成される（向きは重ねられた側（親）→ドラッグした側（子）。新しいアイデアを作って親に重ねる操作が自然なため）。ドロップ後、ドラッグしたノードは開始位置へ自動で戻る（「重ねる」は接続ジェスチャであり移動ではない）。既に接続済みの相手（向き・双方向問わず）はハイライトされず、ドロップしても通常の移動になる。複数選択ドラッグ中・グループノードは対象外（Phase 40） |
| エッジ削除 | エッジを選択してDelete、またはメニューから削除 |
| エッジスタイル | 曲線（bezier）・折れ線（smoothstep）・直線（straight）の3種からユーザーが選択可能。設定パネル「外観」セクションの3択ボタンで切替。選択は localStorage に永続化され全エッジに即時反映される（Phase 21-F） |
| ラベル | エッジに関係性を示すラベルを付けられる（任意）。右クリックメニュー「ラベルを編集」→ アプリ内の入力ダイアログで設定し、エッジ中央に白背景ラベルで表示される。空のまま保存するとラベルを削除する（Phase 21: FloatingEdge の不具合修正 / Phase 30: `window.prompt` から置換） |
| 双方向矢印 | 右クリックメニュー「双方向にする」で両端に矢印を付けられる（Phase 21: FloatingEdge の不具合修正） |

### 2.2 AI拡張機能（Claude連携）

#### 2.2.1 基本動作フロー
1. ユーザーがノードを選択
2. 「AIに拡張を依頼」ボタンをクリック
3. Claude APIにノードのテキストと周辺コンテキストを送信
4. AIが関連アイデアを3〜5個提案（タイトル20字以内 + 補足説明 body に分離して生成）（Phase 18）
5. ユーザーが採用したい提案を選択
6. 選択した提案が新しいノードとして追加・接続される

#### 2.2.2 AI提案の種類
- **関連アイデア**: 選択ノードに関連する概念・アイデア
- **深掘り**: 選択ノードをより詳細に分解した子アイデア
- **対比・反論**: 反対意見や別の視点
- **応用**: 実際の活用方法・具体的な事例

#### 2.2.3 コンテキスト送信
- 選択したノードのタイトルと本文（body）
- 親ノード・子ノードのタイトル（直接繋がるノード）
- マップ全体のノードタイトルリスト（概要把握のため）
- カテゴリ一覧（AIが提案ノードのカテゴリを自動判定するため）
- 重複回避のための除外リスト：追加先モードに応じて対象が変わる。**子ノードとして追加**する場合は選択ノードの既存の子のタイトルを、**兄弟ノードとして追加**する場合は既存の兄弟のタイトルをAIに渡し、既存アイデアと重複する提案を避けるよう指示する。個別再生成時はさらに同一バッチ内の他の提案タイトルも重複禁止に加わる

### 2.2.4 AIチャット機能（Phase 14）

マップ全体をコンテキストとした自由形式の継続会話を提供する。

| 機能 | 説明 |
|------|------|
| マップコンテキスト会話 | 全ノード・エッジ・カテゴリ情報をAIに渡し、マップについて自由に対話できる |
| @ノード参照 | 入力中に `@` でノードタイトルのオートコンプリートが表示される（↑↓/Enter対応） |
| クイック質問チップ | ノード選択時に「深掘り」「反論」「アクション化」「関連提案」「次のステップ」の定型質問ボタンを表示 |
| ワンクリックアクション | AI回答に提案が含まれる場合、ボタン1クリックでノード追加・接続・更新を実行 |
| 会話履歴クリア | セッション内履歴（最大40件）を手動でリセット可能。元に戻せないため実行前に確認ダイアログを表示する（Phase 30） |
| パネルトグル | ヘッダー「AIチャット」ボタンまたは `Ctrl+Shift+C` でパネル開閉 |

### 2.2.5 AI連携UXの改善（Phase 23）

| 機能 | 説明 |
|------|------|
| APIキー未設定ガイド | AI機能実行の前提（Claude・OpenAI=APIキー、Ollama=使用モデル選択）が未設定の場合、AI の3パネル（提案・チャット・分析）でボタン等を非表示にし、アイコン＋案内文＋「設定を開く」ボタンを表示する。設定ボタン押下で設定パネルが開く。文言は選択中のAIプロバイダに応じて出し分ける（Claude: 🔑「Claude APIキーが必要です」／ OpenAI: 🔑「OpenAI APIキーが必要です」／ Ollama: 🖥️「使用するOllamaモデルが未選択です」。Ollamaの選択肢はデスクトップ版のみ。Phase 35、OpenAI追加はPhase 39） |
| チャットストリーミング表示 | AIチャットの応答を一括表示ではなく逐次（ストリーミング）表示する。最初のトークンが届くまでは3点ローディングドットを表示 |
| チャット生成の停止 | 生成中は送信ボタンが「■ 停止」ボタンに変わり、クリックで生成を中断できる。中断時はそれまでに届いたテキストを表示したまま停止する |
| 提案生成のキャンセル | 提案生成中にローディング横の「キャンセル」ボタンで中断できる。キャンセル時はエラー表示なし |
| マップ分析のキャンセル | マップ分析パネルの3タブ（全体分析・つながり・グループ）とも、実行中にローディング下の「キャンセル」ボタンで中断できる。キャンセル時はエラー表示なし（Phase 35。ローカルLLMは応答が長くかかりうるため） |
| エラーメッセージ日本語化 | 401/429/529/ネットワークエラーを日本語の分かりやすいメッセージで表示する（`toFriendlyAIError`） |
| 提案追加後のフォーカス移動 | 提案をマップに追加した後、追加したノード群（子モード: 選択ノード＋追加ノード、兄弟モード: 親ノード＋追加ノード）に fitView でスムーズに移動する |
| chatWithMap の system 化 | マップコンテキストを第1ユーザーメッセージではなく `system` パラメータで渡す。毎回最新マップを反映でき、会話履歴を汚染しない |

### 2.2.6 Web検索（デスクトップ版のみ、Phase 35 追加実装）

AIに聞く前に、最新情報をWeb検索で取得してから回答させるかを選べる。

| 機能 | 説明 |
|------|------|
| 検索トグル | アイデア提案パネル・AIチャットパネル・マップ分析パネル（全体分析タブのみ）にトグルを表示し、実行前にオン/オフを選べる。接続提案・グループ提案タブには置かない（マップ内部の構造を扱うため外部情報が効かない） |
| 検索バックエンド | ollama.com の Web Search API（`POST https://ollama.com/api/web_search`）。ローカルの Ollama サーバーとは別で、ollama.com アカウントで発行するAPIキー（Bearer認証）が必要 |
| 取り込み量 | 上位5件、1件あたり本文600文字に切り詰めてプロンプトに埋め込む（スニペットのみ。本文の追加取得はしない） |
| 検索クエリ | アイデア提案=起点ノードのタイトル＋ユーザーの追加指示／マップ分析=先頭5ノードのタイトル／AIチャット=直近のユーザー発言 |
| 出典表示 | 実行後に参照した情報源（タイトル・URL）を一覧表示し、クリックで既定ブラウザに開く |
| APIキー設定 | 設定パネルの「Web検索」セクションでキーの入力・検索テスト・削除ができる。ollama.com のキー発行ページへのリンクを表示 |
| 既定値 | 既定でオフ。設定パネルの「既定でWeb検索を使う」トグルで各パネルの初期状態を変更できる |
| 対象プラットフォーム | デスクトップ版のみ（`HttpAdapter.canAccessLocalServers` が true のときだけUIを表示）。ブラウザからは CORS 制約で ollama.com のAPIを直接叩けないため |
| 注意事項 | 検索クエリ（ノードタイトル・チャット入力等）は ollama.com に送信される旨を設定画面に明記する |

### 2.2.7 マップ→成果物生成（Phase 45）

マップ全体、または選択ノードのサブツリーを元に、AI が Markdown 形式の成果物をストリーミング生成する。

| 機能 | 説明 |
|------|------|
| 形式 | ドキュメント（要約＋階層を見出しに対応させた構造化記事）／スライド（Marp互換Markdown、`---` 区切り）／タスクリスト（`- [ ] ` のチェックボックス形式、フェーズ見出し付き）の3種から選択 |
| 対象範囲 | ノードを選択中は既定でそのサブツリー（選択ノードを起点に子方向へ辿った範囲）のみを対象にする。トグルでマップ全体に切り替え可能。未選択時はマップ全体 |
| 生成 | ストリーミングでプレビューに逐次表示。生成中はキャンセル可能 |
| 出力 | 「コピー」でクリップボードへ、「.mdで保存」でMarkdownファイルとして書き出し |
| 入口 | ヘッダーの「成果物を作成」ボタン、またはエクスポート/インポートパネルのエクスポートタブから開く |
| 前提条件 | APIキー未設定・Ollamaモデル未選択時は `ApiKeyRequired` の案内を表示（他のAIパネルと同様） |

### 2.2.8 AIガーデナー（マップレビュー、Phase 47）

マップ全体をAIが庭師のようにレビューし、育てるための提案を出す。マップ分析パネルの第4タブ「🌱 ガーデナー」から利用する。

| 機能 | 説明 |
|------|------|
| 実行 | 「マップをレビュー」ボタンでAIがマップ全体を解析し、最大6件の提案を生成する |
| 提案の種類 | 🌱深掘り（放置されている、または内容が薄いノードを掘り下げる子アイデアを提案）／🔗統合（内容が重複・類似する2件のノードの統合を提案）／🌉橋渡し（つながっていない離れたノード同士の接続を提案）／❓問いかけ（マップ全体で抜けている観点を新しいノードとして提案） |
| 放置ノードの判定 | ノード単位の更新日時（`updatedAt`、Phase 49）を持つノードは、最終更新から30日以上経過していれば放置とみなす。`updatedAt` を持たない旧ファイル由来のノードは、従来どおり「子ノードを持たない葉ノードで本文が空、またはAIが作成したまま誰も手を入れていない」という構造的な指標にフォールバックする。判定結果はAIへのプロンプトに「参考」として渡され、深掘り提案のヒントに使われる |
| 適用 | 提案ごとに「適用する」ボタンでワンクリック適用できる。深掘り・問いかけは新規ノードを追加（対象ノードがあれば接続）、統合は本文を連結してエッジを張り替え、橋渡しはノード間を接続する。適用済みの提案はカードが「適用済み」表示になり再適用できない |
| キャンセル | 実行中はローディング下の「キャンセル」ボタンで中断できる（他のマップ分析タブと同様） |
| 前提条件 | APIキー未設定・Ollamaモデル未選択時は `ApiKeyRequired` の案内を表示する |

### 2.2.9 ペルソナ壁打ち会議（Phase 48）

選択したノードについて、複数の視点（ペルソナ）からAIに意見を出させ、採用したい意見を子ノードとして一括追加できる。

| 機能 | 説明 |
|------|------|
| 入口 | ノードの右クリックメニュー「🎭 ペルソナで壁打ち」、またはノード詳細パネルの「🎭 壁打ち」ボタン |
| ペルソナ選択 | プリセット4種（楽観家・批評家・顧客・投資家）をトグルチップで選択、または自由入力で追加できる（例:「高齢のユーザー」）。1つ以上の選択が必須 |
| 意見生成 | 「議論を始める」ボタンで、選択した全ペルソナ分の意見を1回のAI呼び出しでまとめて生成する（ペルソナごとに1〜3件）。生成中はキャンセル可能 |
| 意見の選択 | 生成結果はペルソナごとにカード表示され、意見ごとにチェックボックスで採用/非採用を切り替えられる。生成直後は全件が選択済みの状態になる |
| 子ノード追加 | 「選択した意見を子ノードとして追加」ボタンで、選択した意見を対象ノードの子ノードとしてまとめて追加する。ノード・エッジの追加は1回の操作として履歴に積まれ、Undo 1回で全て取り消せる |
| やり直し | 「議論をやり直す」ボタンで、選んだペルソナ構成のまま再生成できる |
| 前提条件 | APIキー未設定・Ollamaモデル未選択時は `ApiKeyRequired` の案内を表示する |

### 2.3 データ管理

#### 2.3.1 Googleドライブ連携
| 機能 | 説明 |
|------|------|
| 認証 | Google OAuth 2.0でサインイン |
| 保存 | マップをJSONファイルとしてGoogleドライブに保存 |
| 読み込み | Googleドライブ内のマップファイルを一覧表示・読み込み |
| 自動保存 | ノード・エッジ・タイトルの変更から数秒後に自動保存（デバウンス処理）。保存先は現在開いているファイルで、新規作成・インポート時は新規ファイルを作成し既存ファイルを上書きしない |

|------|------|
| 履歴の記録 | 正式な保存（新規保存確定時・上書き保存成功時）が成功するたびに、マップ（`mapId`）単位でスナップショットを端末内に記録する。保存先未確定のローカル控えのみの保存では記録しない |

### 2.3.10 非同期共同編集（Drive 共有フォルダ経由の3方向マージ、Phase 53）

複数人が同じ Google Drive 共有フォルダ内のマップファイルを非同期に編集したときに、保存時の衝突を可能な限り自動統合する。**Drive フォルダの共有操作自体（誰とフォルダを共有するか）は Google Drive の UI 側で行う前提とし、IdeaMap 内には共有設定UIを持たない。** リアルタイムの共同編集（複数人が同時に同じマップを編集し、互いの変更が即座に反映される方式）は非対応（8. 将来的な拡張参照）。

| 機能 | 説明 |
|------|------|
| 衝突検出 | 上書き保存前に保存先の `mapId` を確認し、自分が最後に読み込んだ内容と異なる場合（＝他人が先に保存した）衝突として検出する（既存機能） |
| 3方向マージ | 衝突検出時、従来の「上書き保存」「最新版を読み込む」に加えて「マージを試す」を選べる。前回読み込み/保存時点（base）・自分の現在の編集（mine）・保存先の最新版（theirs）を比較し、片方だけが変更した箇所は自動的に採用する |
| 衝突の絞り込み | 双方が base から同じ箇所を異なる内容に変更した場合のみ「衝突」として扱う。双方が同じ内容に変更した場合や、片方のみの変更は衝突にせず自動統合する |
| 衝突解決ダイアログ | 自動統合できなかった衝突がある場合のみ表示される。ノード・エッジごとに自分の変更／相手の変更のどちらを採用するかを選び（一括選択も可能）、「適用」で確定するとマージ結果を保存する |
| 衝突なしの場合 | マージ結果に衝突が0件なら、ダイアログを出さずそのまま自動的にマージ結果を保存する |
| マージの基準（base） | マップを開いた時点・保存が成功した時点のたびに、その内容を次回マージの基準として端末内に保持する。この基準データがない場合は「マージを試す」を選んでもトーストで案内し、従来の二択にとどまる |
| 対象範囲 | 保存先の種別（Google Drive／ローカルファイル）を問わず、上書き保存の衝突ダイアログが出る場面すべてで使える。想定利用シーンは Drive 共有フォルダ経由の非同期共同編集 |

### 2.4 グループノード機能（Phase 12）

#### 2.4.1 グループの作成・管理

| 操作 | 説明 |
|------|------|
| グループ作成 | 右クリックメニュー「グループを作成」からキャンバス任意位置に作成 |
| 複数ノードのグループ化 | 2つ以上のアイデアノードを選択した状態で右クリック → 「グループ化（N件）」 |
| グループ解除 | 右クリックメニュー「グループを解除（子ノードは残す）」 |
| グループと子を一括削除 | 右クリックメニュー「グループと子ノードを削除」。確認ダイアログでは「このグループと、中の子ノードをすべて削除します。子ノードを残したい場合は『グループを解除』を使ってください。」と伝える（Phase 30: 選択肢が1つしかないのに2択を促していた文言を修正） |
| グループ名編集 | グループ上でダブルクリック、または右クリックメニュー「ラベルを編集」→ アプリ内の入力ダイアログで変更（Phase 30: `window.prompt` から置換）。空のまま保存すると「グループ」に戻る |
| グループリサイズ | グループを選択してハンドルをドラッグ（NodeResizerコンポーネント） |

#### 2.4.2 フリーノード → グループへのドラッグイン

1. フリーノードをドラッグ中、グループ枠と重なるとグループが青くハイライトされる
2. グループ上でドロップ（mouseup）した瞬間に確認ダイアログを表示：
   - **「グループに追加」「追加」「キャンセル」**
3. 「追加」確認 → ノードはグループの子になり、位置は相対座標に変換される
4. 「キャンセル」 → ノードはグループの外に押し出される（最小移動距離で隣接位置へ）

**境界判定**：ノードの任意部分がグループ枠内に重なったとき（矩形 AABB 交差判定）

#### 2.4.3 子ノード → グループ外へのドラッグアウト

1. グループ内の子ノードをドラッグし、ノードの**中心点**が親グループ枠の外に出た時点で確認ダイアログを表示：
   - **「グループから外す」「外す」「キャンセル」**
2. 「外す」確認 → ノードはフリーノードになり、絶対座標に変換される
3. 「キャンセル」 → ノードはグループ内に戻される（`clampNodeInsideParent`）

境界判定の基準：ノードの中心（エッジではない）がグループ外に出た時

- これにより、大きめのノードがグループ端付近にいても誤検知しない

#### 2.4.4 グループリサイズ後の境界整合性

- グループをリサイズした後も、ドラッグアウト/ドラッグイン/clamp/シリアライズのすべてが**リサイズ後のサイズを参照する**
- 整列（Auto Layout）によってグループ内ノードが再配置された後も同様
- 技術的背景：`@xyflow/react` の `applyNodeChanges` は `dimensions` change に対して `node.style.width/height` を更新しないため、resize end イベントで `style` を手動同期する

#### 2.4.5 NodeActionBar（AI拡張/詳細/DEL ボタン）の表示位置

- アイデアノードを選択したとき、選択ノードの**直下中央**に NodeActionBar を表示
- グループ内の子ノードを選択した場合も同様に直下中央に表示
- 技術的背景：子ノードの `position` は親グループからの相対座標のため、スクリーン座標変換には `グループ位置 + 子ノード位置 = 絶対座標` を計算した上で `flowToScreenPosition` を使用

#### 2.4.6 グループ内でのノード接続作成

- グループ内の子ノードから「アイデアを作成（接続）」（Tabショートカット or 右クリックメニュー）を実行した場合、新規ノードは**元のノードと同じグループに属した状態**で必ずグループ内に作成される
- グループを自動拡張しない（外部ノードを取り込む副作用を避けるため）
- 配置位置の優先順位：**右 → 下 → 左 → 上** の順に試し、グループ内に完全に収まる最初の方向を採用する
- 4方向すべてがグループ枠をはみ出る場合は、はみ出し量が最小の方向をグループ内にクランプして配置する
- グループ外のフリーノードから接続作成した場合は従来通り右側 +280px に配置する

#### 2.4.7 グループ内子ノードのドラッグ制約

- 子ノードはグループ枠内でのみドラッグ可能（枠外ドラッグ → ダイアログ表示）
- グループ自体をドラッグすると、子ノードは一緒に移動する（React Flow の `parentId` 機構）
- フリーノードをドラッグ中は、子ノードの「グループに追加」ハイライトは表示しない

#### 2.4.7 コンテキストメニュー（グループ内子ノード）

### 3.2 パフォーマンス
- ノード数100個以下でスムーズな操作（60fps）
- 初回ロード3秒以内
- AI応答は最大30秒のタイムアウト表示
- 大規模マップ（100ノード超）では `onlyRenderVisibleElements` により画面外ノードの DOM 描画をスキップしてパン・ズームを軽量化する（Phase 24）
- JS バンドルはベンダー（React / React Flow / Anthropic SDK）ごとにチャンク分割し、単一チャンクにしない（Phase 28）
- 整列（dagre）・画像エクスポート（html-to-image）に必要なライブラリは初回ロードに含めず、実行時に遅延ロードする（Phase 28）
- ノードの選択・ドラッグで、無関係なノード・パネル・ツールバーを再描画しない。フォーカス表示の dim は各ノード・エッジが自分の状態だけを判定する（Phase 28）

### 3.2.1 ダークモード（Phase 24 / Phase 30 / Phase 33）

ダークモードは全 UI コンポーネントで一貫して機能すること。具体的には以下のすべてが対応する:
- ツールバー（Toolbar）・ボトムナビ（BottomNav）
- キャンバス背景（Background）・コントロール（Controls）・ミニマップ（MiniMap）
- ノードアクションバー（NodeActionBar）
- ウェルカムモーダル（WelcomeModal）
- ヘッダー・各種パネル（既対応）・ContextMenu・ConfirmDialog・Toast・SearchBar（既対応）
- AI提案パネル（AISuggestionPanel）・設定パネル（SettingsPanel）・マップ一覧（MapListPanel）・入力ダイアログ（InputDialog）（Phase 30）
- キャンバスの「掴む」カーソル（Phase 33）: ブラウザ標準のカーソルはフチが細くライトモードの背景と同化して見えないため、白塗り＋黒フチの自前のカーソルに差し替える。ライトでは黒フチが、ダークでは白塗りが背景から浮くため、テーマごとに切り替えず1種類で両テーマとも視認できること。標準カーソルと同程度に細身であること

ただし、ユーザーが選んだカテゴリ色を背景に敷く要素（ノード本体・カテゴリ行・カテゴリチップ）はライト/ダークで配色を変えない。明るいパステル背景の上で文字色だけを反転させると読めなくなるため。

### 3.2.2 アクセシビリティ（Phase 30）

キーボードとスクリーンリーダーでの基本操作が破綻しないこと。

- モーダル（確認ダイアログ・入力ダイアログ・ノード詳細・操作ガイド・マスターパスワード）は `role="dialog"` / `aria-modal="true"` を持ち、見出しと関連付ける（`aria-labelledby`）
- モーダル表示中は Tab フォーカスがモーダル内に留まり、閉じたら開く前の要素へ戻る
- コンテキストメニューは `role="menu"` / `role="menuitem"` を持ち、カテゴリ選択は `role="menuitemradio"` + `aria-checked` で現在値を伝える
- AIチャットのメッセージ一覧は `role="log"` / `aria-live="polite"` で新着を読み上げる（ストリーミング中の逐次更新は読み上げ対象にしない）
- アイコンのみのボタンには `aria-label` または `title` を付ける

### 3.3 セキュリティ
- Claude APIキーはマスターパスワード方式で暗号化してlocalStorageに保存（サーバーに送信しない）
  - ユーザーが任意に設定するマスターパスワードで PBKDF2 + AES-GCM 暗号化（`ideamap-apikey-mp`）
  - マスターパスワード未設定時はAPIキーをセッション内メモリのみで保持（リロードで消える）
  - 起動時にロック状態を検出し、マスターパスワード入力モーダルを表示（`MasterPasswordModal`）
  - スキップ可能（AI機能なしで閲覧のみ使用できる）
  - 旧形式（ハードコードパスフレーズ `ideamap-v1`）で保存された既存キーは起動時に自動移行し、マスターパスワード設定を促す（Phase 27）
- Markdown 描画は DOMPurify でホワイトリストサニタイズ（XSS対策、Phase 27）
  - 許可タグ: `h1, h2, h3, strong, em, code, li, br`
  - 許可属性: `class`
- Google OAuth トークンは標準的なセキュリティプラクティスに従う
- APIキーを含むデータは外部サービスに送信しない
- Anthropic Console での利用上限設定とアプリ専用キーの使用を推奨

### 3.4 オフライン対応
- Googleドライブ未接続時はlocalStorageに一時保存
- 再接続時に同期
- Web版はPWA化されており（Phase 51）、Service Workerがアプリシェルをキャッシュしてオフラインでも起動できる
- オンライン復帰（`online`イベント）をきっかけに、保留していた保存の再試行を自動的に発火させる。credentialKey（Web版はアクセストークン）が変化しない間はこの仕組みがないと再送されなかった既知バグを解消した（Web版・デスクトップ版共通のロジック）
- オフライン中の保存失敗は、オフラインバナー（ヘッダー）が既に状態を示しているため、失敗のたびにトーストを重ねて表示しない

### 3.5 保守性・信頼性（Phase 41〜43）
- **自動テスト**: `packages/core` にユニットテスト（Vitest）を整備し、純粋ロジック（現状は JSON パース処理 `safeParseJson`）から検証を始める。テストは対象ファイルと同じディレクトリに `*.test.ts` として同居させる方式
- **CI連携**: GitHub Actions（`deploy.yml`・`release-desktop.yml`）のビルドジョブ内で `pnpm test` を実行し、テストが赤ならデプロイ（GitHub Pages）・リリース（デスクトップインストーラ）を止める
- **依存監視**: Dependabot（npm・cargo・GitHub Actions、週次）で依存パッケージの脆弱性・更新を継続監視する。minor/patch 更新は1本のPRにグループ化する
- **エラーログ**: 未捕捉エラー（`window` の `error`/`unhandledrejection`）を端末内にリングバッファ形式で最大200件保存する。外部エラー監視サービス（Sentry等）は導入せず、記録は端末内にのみ留める方針。不具合報告の際は設定パネルからテキストファイルとしてエクスポートできる

| 機能 | 要件 |
|------|------|

## 5-B. デスクトップアプリ版の要件（Phase 32〜）

### 5-B.1 デスクトップ版を作る理由

**ローカルLLM（Ollama）を使えるようにすること。** ブラウザから `http://localhost:11434` の Ollama を叩く構成は、ユーザー側の CORS 設定（`OLLAMA_ORIGINS`）に依存し、GitHub Pages 配信の Web 版では安定して提供できません。Tauri の Rust プロセス経由であればブラウザの CORS 制約を受けずにアクセスできます。

### 5-B.3 Web版との差異

| 機能 | Web版 | デスクトップ版 v1 |
|---|---|---|
| ローカルLLM（Ollama） | 非対応 | **対応**（デスクトップ版の存在理由。Phase 35 で実装済み。接続テスト・チャット・マップ分析は実機確認済み） |
| Web検索（AIに聞く前の最新情報取得） | 非対応 | **対応**（ollama.com の Web Search API。Phase 35 への追加実装。アイデア提案での実検索・出典表示まで実機確認済み） |
| Claude API | 対応 | 対応（Phase 34 で実装済み。Rust側 tauri-plugin-http 経由） |
| 保存先 | Google Drive 中心 + localStorage | ローカルファイル中心（Phase 34 で実装済み）。Phase 38 で Drive も明示的な保存先として追加（既定はローカルのまま） |
| Google Drive 同期 | 対応（GISポップアップ認証） | **対応**（Phase 38 で実装。認証はループバック+PKCE、OS既定ブラウザで行う。実機での認可・読み書き確認は未了） |

Web版で作成したマップは JSON エクスポート → デスクトップ版で「開く」で持ち込めます（`MapFile` 型が共通のため変換不要）。

### 5-B.4 非機能要件

- コアロジック（型・ストア・レイアウト計算・LLM呼び出し）は Web版・デスクトップ版で**単一のソースを共有**すること。同じロジックを二重に実装しない
- Web版の既存の挙動・見た目を、共通化作業によって変えないこと
- デスクトップ版で日本語入力（IME）が正常に動作すること（Phase 34 で最優先検証）
- デスクトップ版は当面コード署名なしで配布する。SmartScreen / Gatekeeper の警告についてユーザーに案内すること
- Web版とデスクトップ版のアプリケーションバージョンは単一の真実（ルート `package.json`）から配布物へ同期し、ズレがあればCIで検知すること（Phase 36）
