# IdeaMap バージョンアップロードマップ（提案）

起案日: 2026-08-17（現状: Phase 40 / v0.1.0）

このドキュメントは中長期の方向性の提案。採用が決まった項目だけを `implementation-plan.md` にフェーズとして起票する。

---

## 1. 現状認識

- 機能面は「マップ編集＋AI発散支援」としてすでに充実している（提案・チャット・分析・プレゼン・Drive・デスクトップ版）。
- 一方で **AIの出番が「発散」に偏っている**。アイデアを入れる入口（白紙のキャンバス問題）と、育てたアイデアを取り出す出口（成果物化）が弱い。
- 基盤面は **自動テストが実質ゼロ**（verify スクリプト2本と Rust の一部テストのみ）、CI は型検査＋ビルドのみ。🔨（実機確認待ち）フェーズが11個滞留している。

方針: **「入口 → 育てる → 出口」の価値ループを完成させる**ことを機能面の軸に、その前提として品質基盤を一度固める。

---

## 2. マイルストーン概観

| バージョン | テーマ | 内容 |
|---|---|---|
| **v1.0** | 信頼できる土台 | 残債返済（🔨消化）・テスト基盤・セキュリティ仕上げ・性能ベースライン |
| **v1.1** | 入口と出口 | ブレインダンプ→マップ生成、マップ→成果物生成、思考フレームワークテンプレート |
| **v1.2** | 育てるAI | AIガーデナー（マップ定期レビュー）、ペルソナ壁打ち会議 |
| **v1.3** | 記憶と表現 | ノードのリッチ化（画像・URLカード）、バージョン履歴とタイムラプス再生 |
| **v2.0** | どこでも・つながる | PWA＋オフライン、マップ横断リンク・検索、非同期共同編集 |

順序は「基盤 → 単体で完結する機能 → データ形式に影響する機能 → 同期を伴う機能」の依存順。v1.1 と v1.2 は独立なので入れ替え可。

## 3. v1.0 — 信頼できる土台（基盤リリース）

新機能なし。以後のすべての機能開発の速度と安全性を上げるための投資。ここを終えたら胸を張って v1.0 を名乗る。

### 3.1 残債返済（🔨フェーズの確定）
- 実機確認待ちの11フェーズ（25/26/27/31/33/35/36/37/38/39/40）のチェックリストを消化し、✅化する。
- 特に効果が大きいもの: デスクトップ版 Drive の実機認可（Phase 38）、OpenAI 実キー疎通（Phase 39）、デスクトップ配布一式の開発機以外での確認（Phase 36）。

### 3.2 テスト基盤の導入
- Vitest を導入し、`packages/core` から始める（純粋ロジックの塊でテスト対効果が最も高い）。
  - 対象: mapStore の各スライス（Undo/Redo 含む）、レイアウト計算、LLM プロバイダのパース処理（SSE・エラー分類）、`driveService` のリクエスト組み立て。
  - 既存の `verify-openai.mts` / `verify-radial-layout.mts` は Vitest に移植して一本化。
- CI（deploy.yml / release-desktop.yml）にテスト実行ステップを追加。テストが赤ならデプロイもリリースも止まるようにする。

### 3.3 セキュリティ仕上げ
- Web版に CSP メタタグを追加（現状デスクトップ版のみ）。`connect-src` を Anthropic / OpenAI / Google API に限定。
- Dependabot（または `pnpm audit` の CI 組み込み）で依存脆弱性を継続監視。
- Google OAuth 同意画面を「In production」化（Testing のままだとリフレッシュトークンが7日で失効する既知課題の解消）。

### 3.4 性能ベースラインとエラー可視化
- 500／1000ノードのベンチマークマップを作り、初期描画・ドラッグ・自動整列・Undo の所要時間を計測して記録する（対策は計測結果が出てから。先回りの最適化はしない）。
- グローバルエラーハンドラでエラーをローカルログ（リングバッファ）に貯め、設定画面から「ログをエクスポート」できるようにする。外部監視サービス（Sentry 等）はバックエンドなし方針に合わないため導入しない。

## 4. v1.1 — 入口と出口（AI機能の第2幕）

「アイデアを育てる」の前後を埋め、アプリの価値ループを完成させる。**機能面で最も大きなレベルアップ。**

### 4.1 ブレインダンプ → マップ生成（入口）
- テキストを貼り付ける（または書き殴る）と、AIが構造を抽出してマップを生成する。議事録・メモ・箇条書きが対象。
- 新規マップ生成と、**既存マップへの追記**（どのノードにぶら下げるかもAIが提案）の両対応。
- 白紙のキャンバス問題を解消する。マップ全体をコンテキストに渡す仕組みは AIチャットで実装済みなので、その逆方向（構造化出力→ノード生成）を作る。

### 4.2 マップ → 成果物生成（出口）
- マップ（または選択したサブツリー）から、AIが文章の成果物を生成する:
  - **構造化ドキュメント**（Markdown: 企画書・ブログ下書き・READMEなど、用途をプロンプトで選択）
  - **プレゼン構成**（既存のプレゼンテーションモードの発表リストを自動生成。さらに Marp 形式の Markdown 書き出しでスライド化）
  - **タスクリスト**（アイデアを実行計画に変換）
- 生成結果はプレビュー→クリップボード／ファイル保存。まずは Markdown 一本で始める。

### 4.3 思考フレームワークテンプレート
- SWOT・KPT・5Whys・オズボーンのチェックリスト・マンダラートなどを「テンプレートマップ」として用意し、新規作成時に選べるようにする。
- 各テンプレートに専用のAIプロンプトを紐付ける（例: SWOT の「脅威」ノードでは脅威に特化した提案を出す）。
- 実装は軽い（初期ノード配置＋提案プロンプトの差し替え）割に、発想支援ツールとしての説得力が大きく上がる。

## 5. v1.2 — 育てるAI（コンセプトの深化）

「AIと一緒に育てる」を、受け身（頼んだら提案）から能動（AIが気づく）へ進める。

### 5.1 AIガーデナー（マップレビュー）
- ボタン一発（またはマップを開いたとき）で、AIがマップ全体を庭師のようにレビューする:
  - 長く放置されているノードの深掘り提案（ノードに `updatedAt` を持たせる）
  - 内容が重複しているノードの統合提案
  - つながっていないクラスタ同士の橋渡し提案（既存の接続提案の発展）
  - 「この観点が抜けていませんか？」という問いかけ
- 結果は既存のマップ分析パネルの体裁で表示し、ワンクリックで適用。既存の分析3機能（全体分析・接続提案・クラスタ提案）を包含・統合する形で設計する。

### 5.2 ペルソナ壁打ち会議
- ノード（またはサブツリー）を指定して「楽観家・批評家・顧客・投資家」など複数ペルソナに議論させ、各視点の意見を子ノードとして展開する。
- ペルソナはプリセット＋自由定義。1回のLLM呼び出しで複数視点を構造化出力させれば、コストも実装も重くならない。
- AIチャットの@メンション・ワンクリックアクション基盤を再利用する。

## 6. v1.3 — 記憶と表現

データ形式（`.ideamap` / 共有URL / Drive 保存）に手が入るため、テスト基盤（v1.0）が整ってから着手する。

### 6.1 ノードのリッチ化
- 画像添付（Drive またはローカルファイル参照＋サムネイル埋め込み）と、URLカード（リンク先タイトルの取得・表示）。
- スキーマ変更を伴うため、`.ideamap` フォーマットのバージョンフィールドとマイグレーション処理をこのタイミングで整備する（以後の全スキーマ変更の下敷きになる）。

### 6.2 バージョン履歴とタイムラプス
- 保存時スナップショット（ローカル）＋ Google Drive の revisions API を使った履歴閲覧・任意時点への復元。
- おまけとして「タイムラプス再生」: マップが育っていく過程をアニメーションで再生する。「育てるアプリ」ならではの演出で、共有したくなる体験になる。

## 7. v2.0 — どこでも・つながる（クラウド編）

### 7.1 PWA化 ＋ オフライン対応
- Web版を PWA 化（インストール可能・Service Worker）。オフライン編集は localStorage 一時保存の既存機構を土台に、オンライン復帰時に Drive へ同期する。
- スマホ実機確認（Phase 25/26 の残債）と同じ流れで検証できる。

### 7.2 マップ横断（ワークスペース）
- ノードから別マップへのリンク、複数マップの横断検索。
- 発展形として、過去マップとの関連をAIが提示する「このアイデア、以前の○○マップとつながっています」。まずは全文検索で実装し、embedding 導入は必要になってから検討する。

### 7.3 非同期共同編集
- リアルタイム共同編集（CRDT＋シグナリングサーバー）は**やらない**。バックエンドなし方針と個人開発の運用負荷に合わない。
- 代わりに Drive 共有フォルダ経由の非同期コラボ: 相手の変更を検知して3方向マージ（ノード単位）、衝突時のみダイアログで解決。デスクトップ版の外部変更検知（Phase 37）の仕組みを土台にできる。
- それでも重い場合は「コメント専用モード」（閲覧＋コメント付箋のみ）まで縮退する選択肢を持つ。

---

## 8. やらないと決めたこと

| 項目 | 理由 |
|---|---|
| 自前バックエンド／リアルタイム共同編集 | バックエンドなし方針の放棄になり、運用負荷が個人開発の範囲を超える |
| Sentry 等の外部エラー監視 | 同上。ローカルログ＋エクスポートで足りる |
| モバイルネイティブアプリ | PWA で賄う。Tauri Mobile は成熟を待つ |
| embedding ベースの意味検索（当面） | まず全文検索で価値を確認してから |
